# 性能与资源

Picsoc 使用分页索引、有界任务队列和按需图片加载，避免素材数量直接决定前端常驻图片数。原图通过流式 HTTP 返回，浏览网格时只请求缩略图。

## 默认资源策略

| 部分 | 当前策略 |
| --- | --- |
| 目录扫描 | 同时扫描一个素材库，100 个文件一批写入索引 |
| 缩略图任务 | 队列最多 64 项，默认 1 个图片 worker |
| 解码 | 原文件最多 256 MiB，解码预算 128 MiB，超限显示占位图 |
| 缓存 | PNG 缩略图写入磁盘，最长边不超过 384px，小图保持原尺寸，内容修改后清理旧版本 |
| 删除索引 | 每批最多清理 200 项及其缩略图 |
| 网格 | 只挂载可见行与少量预加载行 |
| 前端数据 | 每页 100 项，最多缓存 8 页 |
| 目录树 | 按需展开，每层每页 200 个目录，使用索引计数和游标分页 |
| Docker | 默认 1 CPU、512 MiB；图片 worker 为 1 |

解码预算针对解码器及像素缓冲，进程还需要数据库、转换、缩放和运行时内存；它不是进程总内存上限。更多 worker 会增加瞬时内存。第一版默认采用保守的单 worker。

成功生成的已有缓存继续复用，不会因缩略图策略调整而强制重处理整个库。只缩小、不放大的策略适用于新生成的缓存；普通重扫不会重编码未变化的成功缓存。

## 可复现基准

先构建 release 程序，在仓库根目录运行：

```sh
python3 scripts/benchmark.py --binary target/release/picsoc --count 500
```

脚本生成临时 PNG、启动独立本地服务，等待索引和缩略图完成，然后停止进程并清理测试目录。默认使用横、竖、方三种尺寸的纯色 RGB PNG，尺寸由 `--width`、`--height` 派生；`--layout flat` 可使用单一尺寸和平铺目录。默认结构化目录包含当前层图片、子目录、空目录和名称含 `map` 的素材。可通过 `--count` 设置最多 100,000 张图片。

脚本校验分页、目录计数、比例、名字排除和组合条件的准确结果，并测量 HTTP 查询的 p50/p95/最大延迟；`--query-samples` 控制每类查询的次数，`--output` 保存 JSON。Windows 使用 `python` 与 `picsoc.exe`；峰值内存统计仅在提供 `resource` 的 Unix 系统可用。

测试 3.5 万张素材的索引查询：

```sh
python3 scripts/benchmark.py --binary target/release/picsoc --count 35000 --width 64 --height 36 --query-samples 20 --timeout 600 --output benchmark-35000.json
```

这组小图用于验证素材数量、索引访问和有界分页，不代表 15 GB 原图解码负载。测试会临时写入 35,000 个原文件及其缩略图，需要可用磁盘空间。

### 35,000 张素材实测

2026-10-10 在 macOS 15.7.7 / Intel x64 开发机上，分别运行一次修复前后 release 程序。两次均使用 1 worker、新建临时数据目录、35,000 张纯色 RGB PNG（64×36、36×64、36×36），原文件合计 4,130,016 字节，包含多层目录、空目录和名称排除样本。每种 HTTP 查询连续测量 20 次。

| 项目 | 小图被放大的先前实现 | 小图保持原尺寸 |
| --- | ---: | ---: |
| 索引与全部缩略图完成 | 188.164 秒 | 44.457 秒 |
| 服务峰值 RSS | 45.62 MiB | 14.52 MiB |
| 缩略图缓存 | 609,153,634 字节 | 9,426,697 字节 |
| 素材第一页 p95 | 8.320 ms | 5.365 ms |
| 深分页 p95（offset=34,800） | 9.100 ms | 7.380 ms |
| 根目录树 p95 | 11.919 ms | 9.081 ms |
| 排除 `map` p95 | 32.358 ms | 22.973 ms |
| 比例筛选 p95 | 35.950 ms | 21.649 ms |
| 比例、尺寸、方向、排除词、像素排序组合 p95 | 70.968 ms | 38.651 ms |

两次均通过全部 11 类查询的总数、分页边界、目录计数和组合筛选断言。原始报告：[修复前](benchmarks/2026-10-10-35000-before.json)、[修复后](benchmarks/2026-10-10-35000-after.json)。导入完成由 1 秒间隔轮询判定；RSS 只统计服务进程，未包含浏览器。

这两次单机测量说明小图不放大可以显著减少处理时间和缓存。查询延迟也会受到系统负载和缓存状态影响，不应把两次的差值全部归因于缩略图修复。这组输入不模拟 15 GB 素材库、复杂或大尺寸图片、GIF 动画、多个同时使用的浏览器及生产存储。

### 先前的大尺寸输入基准

2026-10-10 的先前版本在开发机上实测，使用优化后的原生程序和平铺目录：

| 项目 | 结果 |
| --- | --- |
| 系统 | macOS 15.7.7 / Intel x64 |
| 输入 | 500 张 1500×1000 的纯色 RGB PNG |
| 并发 | 1 worker |
| 索引与缩略图完成 | 6.521 秒 |
| 服务峰值 RSS | 103.52 MiB |
| 原文件总字节数 | 3,359,000 |
| 缩略图缓存总字节数 | 1,277,000 |

这个基准验证上述输入下的处理与内存表现。纯色 PNG 压缩率高，不能代表复杂照片、超大图片、网络盘或所有机器的导入速度；生产素材应在相同机器上另行测量。

## 调整

- 低配置电脑保持 `--workers 1`，服务启动后使用浏览器访问。
- 定期扫描只处理索引变化；文件较多或素材在网络盘时，可以增加扫描间隔。
- 同时浏览多张原图会使浏览器解码更多像素，浏览器内存与服务内存分别计算。
- 支持的格式无法解码时可尝试下载原文件；修复临时读写问题后手动重扫会重试缩略图。
